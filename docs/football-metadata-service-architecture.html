Football metadata service

Target architecture: logic moves into the service now, storage moves per aggregate later (option D)

Skillcorner

Key decisions

01

One writer per aggregate

The service and wilson never write the same entity at the same time. Running both in parallel is allowed only as shadow: compute, compare, never write.

02

IDs stay wilson IDs

Customer data and wilson's operational foreign keys keep working. The service allocates new IDs only after an aggregate's storage moves.

03

Outbox lives with the write

Until storage moves, the outbox is in wilson's DB and is filled by son signals, so every writer emits events, including ones not migrated yet.

04

ETL = match pipeline

Step Functions run fetch → normalize → resolve → plan → apply for each provider match. Only APPLY PLAN writes, and it does so in one transaction.

Pipeline rules

01

Plan, then apply

Every state before APPLY PLAN writes only to S3, under deterministic keys, so any of them can be retried. APPLY PLAN writes everything in one transaction, so a match is never half-created.

02

S3 keys in state

Executions carry the raw, normalized and plan keys, never the payloads, which keeps state far below the 256 KB limit. Every run can be replayed from raw.

03

Idempotent starts

The execution name is provider:provider_match_id:payload_hash, so Step Functions rejects duplicates. APPLY PLAN takes an advisory lock per provider match and records the plan hash in the inbox.

04

Shadow = same machine

With mode = shadow, DIFF VS WILSON replaces APPLY PLAN. Phase 3 runs every feed in shadow first, then flips provider_feed.owner to fms.

Options

A

HTTP proxy to wilson

Wilson's REST writes are partial and admin-only, every call adds latency, and nothing gets decoupled.

contract prototyping only

B

Parallel crons + REST, own DB

Two writers: two ETLs create the same match under different ids, with no transaction across the two databases.

shadow mode only

C

Replicate (CDC), then flip

A clean model from day one, but months of two-way sync. With no updated_at in wilson, it needs DMS or Debezium.

heavy

D

Strangler at the data layer

The service owns the logic now and reads and writes wilson's DB through son, so wilson's save() rules keep firing. Storage moves per aggregate later by swapping the repository adapter.

recommended

Contracts in skcr-models, ports and son adapters, the pipeline-state and inbox tables, and a wilson MR adding updated_at and the outbox signals.

REST and SQS commands. Writers move over one at a time: pipeline → Macolito → Opta FD → Gaffer → Forest.

3

Match pipeline

feed-sync runs every feed with mode = shadow and reports diffs against what wilson created. Each feed then flips to owner = fms, mode = live, and the wilson Lambda skips feeds the service owns.

DONE WHENevery feed is live on the service and the wilson provider Lambdas are deleted

4

Storage flip

Optional, per aggregate: reference → team / stadium / coach / referee → player → match. Rows keep their ids, the adapter is swapped, and wilson-projector keeps wilson's tables updated.

DONE WHENnothing reads that aggregate from wilson's tables directly
